# 0090. MCP action tools: list_actions / draft_action over the protocol

- **Phase / milestone:** Milestone 12, Unit 4 (plan: spec 0087)
- **Issue:** —
- **Status:** approved (autonomous mode)

## Problem

Unit 3 (spec 0089, ADR 0023) built the grounded-action layer: `draft_action(kind,
domain, question)` returns a field-verified, propose-and-approve `ActionProposal`
strictly from a verifier-checked grounding, and `available_actions()` describes the
declared catalog. That layer is pure-stdlib and CI-tested but, like the M11 grounded
tools before Unit 4 of that milestone, it is not yet reachable over the protocol.

This unit transports it. The MCP server (`tessera.agent.mcp_server`, spec 0084) gains
two thin tools — `list_actions` and `draft_action` — so an enterprise AI agent can
discover the action catalog and ask Tessera to draft a grounded, cited,
verifier-checked **proposal** (or receive a carried refusal) over MCP. The server
stays a thin transport (ADR 0022): it holds **no drafting logic** — both tools
delegate verbatim to the Unit-3 layer.

## The design

**Two MCP-free handlers** (unit-tested in CI without the SDK, the M11 split):

- `tool_list_actions() -> {"actions": available_actions()}` — the declared catalog
  (name, description, the domains and route each draws from), for discovery.
- `tool_draft_action(action, domain, question) -> draft_action(action, domain,
  question).to_dict()` — the serialized `ActionProposal`. A refused/route-incompatible/
  wrong-domain grounding serializes as a carried refusal (`refused=true`, no fields);
  an unknown `action` kind raises `ValueError` (a programming error, surfaced as a tool
  error — the same contract as an unknown domain in `ground`).

**The SDK wiring** registers both in `build_server()` with agent-facing descriptions
that state the propose-and-approve contract (`requires_approval`/`executed`,
`all_grounded` is the per-field-verified guarantee, a refusal is never an action). The
server now advertises **five** tools (`list_domains`, `ground`, `assertions`,
`list_actions`, `draft_action`). `SERVER_INSTRUCTIONS` is extended to name the action
tools and the propose-and-approve posture.

**Packaging is unchanged (the M11 pins hold).** The SDK stays the opt-in `agent` extra,
imported lazily only inside `build_server`/`main`; importing the server module pulls no
`mcp` (the subprocess pin). The action substance carries no MCP dependency. No engine
or frozen-core change.

**The committed "ran on" session.** `scripts/record_mcp_session.py` (the no-spend
analogue of the M5 snapshot) is extended to drive the new tools over a real
client↔server stdio session: `list_actions`, an `incident` drafted from a devex RCA, a
`pr_summary` drafted from a change analysis, and a **carried refusal** (an `incident`
requested from a PR question — route-incompatible). The regenerated `data/mcp_session/`
(TRANSCRIPT.md + session.json) shows every drafted field with its verdict and the
refusal carried, not drafted over.

## Acceptance criteria

- [ ] `tool_list_actions` returns the declared catalog; `tool_draft_action` returns a
      fully-grounded incident (devex + github_actions) and pr_summary (devex), and a
      carried refusal for an incompatible/refused/wrong-domain grounding — each
      JSON-native. Unit-tested in CI (no SDK).
- [ ] `build_server()` advertises the five tools with descriptions and the expected
      input schemas (`draft_action`: `action`, `domain`, `question`); dispatching
      `draft_action` through the server returns the serialized proposal; a refusal
      crosses as a carried refusal. Contract-tested under `--extra agent` (skipped in CI).
- [ ] The no-`mcp`-in-base-graph subprocess pin still holds (unchanged).
- [ ] A committed real client↔server session in `data/mcp_session/` drafts an incident,
      a pr_summary, and carries a refusal — regenerated by
      `uv run --extra agent python scripts/record_mcp_session.py`.
- [ ] Gate green under multiple `PYTHONHASHSEED` values; faithfulness 1.0 on every
      battery; no battery number moves (the server transports a consumer, not a new
      answer path).

## Scope

**In:** `tool_list_actions` / `tool_draft_action` + their `build_server` registration
and descriptions in `tessera/agent/mcp_server.py`; extended `SERVER_INSTRUCTIONS`;
tests in `tests/test_mcp_server.py` (the two handlers + extended contract test);
extended `scripts/record_mcp_session.py` + regenerated `data/mcp_session/`.

**Out:** the action-boundary CI measurement over gold/representative cases (Unit 5,
spec 0091); any change to the Unit-3 drafting logic (`actions.py` is transported
unchanged); any effectful execution / dry-run payload; an LLM anywhere; a new gated
metric; any engine or frozen-core change.

## Eval impact

**None to the gated numbers** — the server transports the Unit-3 consumer; faithfulness
stays 1.0 and no battery number moves. The new tools are exercised by unit/contract
tests and the committed session, not by the eval batteries.

## Risks / open questions

- **The MCP SDK dependency.** Unchanged from M11: opt-in `agent` extra, lazily imported,
  default import graph pinned free of it; the action substance is fully CI-tested and the
  SDK only transports it.
- **Tool error vs carried refusal.** A *refusal* (insufficient/incompatible grounding) is
  data — `refused=true` with a reason, carried; only a true *programming error* (unknown
  action kind) raises. The session demonstrates the carried-refusal path so the
  distinction is visible in the committed artifact.
